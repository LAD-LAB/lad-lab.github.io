The Pipeline
Upgrade

Rewriting the lab’s core data processing workflow for the multiplex era

This is the biggest piece of work. The driving force was the move to multiplex sequencing — pooling trnL and 12S together in a single run. The old code couldn't handle that, so I rewrote it from the ground up.

The journey of a sequencing run

Here's the full journey of a sequencing run. Raw BCL files come off the MiniSeq, get transferred to the Duke Computing Cluster, where they go through demultiplexing with bcl2fastq, then fork into the trnL and 12S QIIME2/DADA2 pipelines running in parallel via SLURM. Those are existing DCC scripts, not mine. What IS mine is everything on the right — Pipeline-to-Phyloseq picks up the output via rsync, handles both markers from one multiplexed run, assigns taxonomy, runs QC, and produces the final phyloseq object locally on Box. That's the R data structure we use for all downstream analysis.

The old Pipeline-to-Phyloseq

The lab’s existing code has served us well for years, but was built for a different era—single-marker runs (trnL or 12S processed separately).

How it worked

  • One marker at a time — separate runs for trnL and 12S, processed independently
  • Manual scp commands to download from DCC
  • Manual unzipping of QIIME2 artifacts to extract read counts
  • Taxonomy via taxonomizr + local NCBI SQL database (~70 GB on Isilon)
  • Missing accessions required manual lookup and hardcoded fixes

The problem: the lab is moving to multiplex sequencing—pooling trnL and 12S together in a single run. The old code wasn’t designed for this and couldn’t handle multiplexed data.

Other limitations: required Isilon-mounted 70 GB SQL database, manual setwd() path management, and significant codebase familiarity.

The old Pipeline-to-Phyloseq has been around for a few years and it worked fine for its era. But it was built for single-marker runs — you'd process trnL separately, 12S separately. You had to scp files from DCC manually, unzip QIIME2 visualization files to get read counts, and taxonomy relied on taxonomizr with a 70-gigabyte SQL database sitting on Isilon. The real breaking point was multiplex: when we started pooling trnL and 12S in the same sequencing run, the old code simply couldn't handle it. That's what forced the rewrite.

The new Pipeline-to-Phyloseq

A complete rewrite built for the multiplex era—trnL and 12S from a single pooled run, processed together from the start.

Built for multiplex

  • Handles multiplexed runs natively — trnL and 12S results are split and processed from one sequencing run
  • rsync downloads with staging directory — replaces manual scp
  • Automated read count extraction — no more unzipping QZV files
  • Custom taxonomy functions (assign_trnL, assign_12S) — exact substring matching via Biostrings, no 70 GB SQL database
  • Template format — change a few variables and run

What stayed

  • ASV collapsing with collapseNoMismatch()
  • Positive/negative control QC
  • Phyloseq as the output format

Goal: a standardized workflow where any lab member can go from multiplex pipeline output → QC’d phyloseq with minimal setup and no manual path construction.

The new version handles multiplex natively — trnL and 12S results from one pooled run are split and processed automatically. rsync replaces manual scp. Read counts are extracted programmatically instead of unzipping QZV files. Taxonomic
Translation

Turning ASV sequences and scientific names into human-readable dietary identifications

Switching gears to a completely different problem. Once we have a phyloseq, the taxa are identified by scientific names or raw sequences. That's fine for analysis, but when we need to interpret results or present them — what did this person actually eat? — we need common names. And that turns out to be surprisingly tricky.

Where this fits

Common name assignment is a post-processing step on the phyloseq output.

Before we dive in, here's where common name assignment fits in the overall workflow. Everything up through the phyloseq — the pipeline we just talked about — gives us scientific names and raw sequences. Common name assignment takes that phyloseq output and translates it into human-readable dietary names. It's a post-processing step — it doesn't change the data, it adds interpretability.

The interpretation gap

Three levels of increasing interpretability:

What the sequencer gives us:

CAAATCCTTTTTATTGTAAAAATTTCGATCGATCG...

↓

What the pipeline tells us:

Fragaria × ananassa; Fragaria vesca; Rosa rugosa; Rubus ursinus; Rubus idaeus...

↓

What we actually need to know:

Strawberries, raspberries, and blackberries

Here's the interpretation gap in three levels. The sequencer gives us raw DNA sequences — meaningless to anyone without a database. The pipeline tells us Latin binomials — Fragaria ananassa, Rosa rugosa, Rubus idaeus — which is better, but imagine putting that in a dietary report for a clinician. What we actually need is: "strawberries, raspberries, and blackberries." Short, common, English names that capture what someone ate. That's the gap this tool fills.

The trnL chloroplast marker is relatively low-resolution, and real sequences are often shorter than the full-length reference—so a single ASV can match dozens of reference species across multiple genera.

This is why it's hard. The trnL marker is relatively low-resolution, and our actual sequences are often shorter than the full-length reference — so a single ASV can be a substring of many reference ASVs, matching dozens of species. This Rosaceae example matches 83 species across 15 genera. We can't list all 83 in a report. We need a system that can look at those 83 species and intelligently decide: this is strawberries, raspberries, and blackberries.

The reference contains full-length ASVs, but real sequences are often shorter—matching to multiple reference entries. What happens when one ASV matches several names?

The foundation is a curated CSV reference database. Each entry maps a full-length trnL ASV to a conventional dietary name. The key columns are the ASV sequence itself, all matching species, and the expert-curated conventional name. But here's the catch: the reference has full-length ASVs, and our real sequences from the pipeline are often shorter — they're substrings. So one real ASV might match multiple reference entries, each with a different name. That's where the resolution logic comes in.

assign_common_names()

An R function that matches ASVs to the reference database and resolves naming conflicts through a multi-level hierarchy.

The function works through a hierarchy. First, it does a substring match against the reference database. If there's exactly one match, we just use that name — simple. If there are multiple matches, it checks whether one ASV's species are a superset of the others — meaning the others are just subsets and the superset name covers them all. If neither of those works, it checks whether all the matched species share the same genus — if so, it can use a genus-level name. And if the species are truly disjoint — different genera, different families — it concatenates the names. The cases get progressively more complex as you go down.

Resolution in action

Concrete examples of how each resolution level works:

Superset Coffea canephora; C. congensis; C. liberica (coffee)  +  Coffea canephora (robusta coffee)  +  Coffea liberica (Liberian coffee)

→ Coffee — robusta coffee and Liberian coffee are subsets of the first ASV’s species, so it absorbs them

Concatenation Nauclea orientalis (canary wood)  +  Vangueria madagascariensis (Spanish tamarind)

→ Canary wood and Spanish tamarind — disjoint species, so names are concatenated

Genus override Pandanus amaryllifolius; P. dubius; P. spiralis; P. tectorius (pandan)  +  Pandanus conoideus (pandan)  +  Pandanus dubius (bakong)

→ Pandan — all species share the genus Pandanus, so genus-level name wins

Processing pipeline

  • Subtype consolidation — “wild rice” + “rice” → “rices”
  • Singular/plural — berries, potatoes, cherries
  • Deduplication & smart concatenation with “and”

Final formatting

  • Oxford comma: “X, Y, and Z”
  • Suffixation: “and other stone fruits”
  • All conflicts logged for auditing
Let me walk through three real examples. Superset: we have three reference ASVs for Coffea — one matches canephora, congensis, and liberica and is called "coffee"; another matches just canephora and is called "robusta coffee"; a third matches just liberica, "Liberian coffee." Since the latter two are subsets of the first, the superset name "coffee" absorbs them. Concatenation: canary wood and Spanish tamarind are completely unrelated species — different families — so we just concatenate: "canary wood and Spanish tamarind." Genus override: multiple Pandanus species match, and while one of them is called "bakong" instead of "pandan," they all share the genus Pandanus, so the genus-level name "pandan" wins. After resolution, there's a processing pipeline for formatting — subtype consolidation, pluralization, Oxford commas, and so on. I'd like others in the lab to test this on their data.

Human Read
Anonymization

Detecting and replacing human DNA sequences in 12S data for SRA deposition and IRB compliance

Now a completely different kind of problem. When we publish our 12S data to the Sequence Read Archive — which we need to do for papers — we can't include human DNA. This is both an ethical concern and an IRB requirement.

Where this fits

The anonymizer pre-processes 12S reads before they enter the DADA2 pipeline.

Before we get into the details, here's where the anonymizer fits. Remember the workflow from earlier — after demux, the reads fork into the trnL and 12S pipelines. The anonymizer sits right here on the 12S branch, before DADA2. It intercepts the raw FASTQ files, replaces any human sequences, and passes the cleaned files into the pipeline. The trnL branch isn't affected — there's no human DNA concern with plant markers.

Why does human DNA appear in our data?

The 12S rRNA marker amplifies DNA from all vertebrates—not just dietary animals.

  • Stool samples contain human epithelial cells
  • Saliva samples contain human buccal cells
  • The 12Sv5 primers are universal vertebrate primers—they bind human mitochondrial DNA just as well as fish or chicken

The concern: raw FASTQ files contain human mitochondrial sequences. When we publish data through SRA (Sequence Read Archive), these must be removed.

IRB compliance: our protocols require removing identifiable human genetic information before public data deposition.

The 12S marker uses universal vertebrate primers — 12Sv5 — that amplify DNA from all vertebrates, including humans. Since our samples are stool and saliva, they're full of human epithelial and buccal cells. So the raw FASTQ files inevitably contain human mitochondrial sequences. When we want to deposit these on SRA, those need to come out. Our IRB protocols also require this. The question is: how do you remove them without breaking everything downstream?

Design principle: replace, don’t remove

Why not simply filter out human reads?

Filtering (problematic)

  • Removing reads changes the total read count
  • Altered counts affect downstream normalization and relative abundance estimates
  • Denoising algorithms (DADA2) expect complete datasets—missing reads distort error models

Replacement (our approach)

  • Read count is preserved exactly
  • File structure (FASTQ format) is unchanged
  • Primer sequences are maintained for downstream trimming
  • Replaced reads are flagged with a recognizable synthetic sequence

Result: anonymized FASTQ files are structurally identical to originals—all downstream tools work without modification.

The key design decision was to replace, not remove. If you just filter out human reads, you change the total read count, which affects normalization and relative abundance estimates downstream. DADA2 also expects complete datasets — removing reads distorts error models. So instead, we replace the human sequence content while keeping the read itself. The read count stays the same, the file format is unchanged, primers are preserved for trimming, and the replacement is flagged with a recognizable synthetic sequence so it can be identified later. The anonymized files are drop-in replacements.

Detection: k-mer matching

Each read’s core region (after stripping primers) is decomposed into overlapping k-mers and compared against a pre-built human reference database.

Detection uses k-mer matching. We strip the primer regions from each read to get the core sequence, then decompose it into overlapping 8-mers — sliding window of 8 bases. Each k-mer is encoded as a base-4 integer for fast lookup. We compare these against a pre-built database of all k-mers from the human mitochondrial genome, both forward and reverse complement. If 70% or more of a read's k-mers match the human reference, it's classified as human. The 70% threshold was tuned to be sensitive enough to catch human reads while avoiding false positives on closely related primates.

Primer-aware replacement

The tool detects R1/R2 reads automatically and preserves primer sequences so downstream trimming tools still work correctly.

↓

Original quality scores are preserved—only SNP positions are set to Q35. For R1/R2 paired reads, only the relevant primer end is kept.

When a read is flagged as human, we do a primer-aware replacement. The tool auto-detects whether it's an R1, R2, or merged read from the filename. The 12Sv5 primers — 18 bases each — are preserved exactly as they were; only the core region between them gets replaced with a recognizable synthetic sequence. For paired-end reads, R1 only has the forward primer and R2 only has the reverse complement of the reverse primer, so the tool handles each case appropriately. A key change from the earlier version: we now preserve the original quality scores rather than generating synthetic ones. This avoids the DADA2 quality-filtering issue I ran into with Ammara's data — only the SNP positions get set to Q35.

Preventing downstream artifacts

If all replaced reads had identical sequences, DADA2 would collapse them into a single ASV—creating a misleading “super-read” in the denoised output.

The problem

Read 1: REPLACE_CORE_SEQ

Read 2: REPLACE_CORE_SEQ

Read 3: REPLACE_CORE_SEQ

→ DADA2 collapses to 1 high-abundance ASV

The solution: fixed SNP positions

Read 1: REPLACE...CARE...SGQ

Read 2: REPLACE...CTRE...SAQ

Read 3: REPLACE...CGRE...SCQ

positions at 33% & 67% of sequence

→ 4² = 16 distinct variants, cycled by read index

Deterministic: the same read index always produces the same variant. The recognizable core prefix still allows identification downstream.

One subtle issue: if we gave every replaced read the exact same synthetic sequence, DADA2 would collapse them all into a single high-abundance ASV — creating a misleading artifact. The earlier version used random SNPs at random positions, but that was unpredictable and made it harder to reason about DADA2's behavior. The new approach uses two fixed SNP positions — at 33% and 67% of the sequence length — and cycles through base substitutions systematically based on the read index. Four choices at each of two positions gives 4-squared equals 16 distinct variants. It's deterministic, so the same read index always produces the same variant. Combined with preserving the original quality scores, this addresses the DADA2 quality-filtering artifacts I was seeing earlier.

Built-in verification

The tool doesn’t just write output—it reads it back and checks its own work.

1

Process — scan each read, identify human sequences, replace cores while preserving primers

2

Write — output anonymized FASTQ.gz with matching read count

3

Verify — re-read the output file and confirm that:

  • Input and output read counts match exactly
  • Every replaced read contains the expected synthetic prefix
  • Original primers are intact on replaced reads

Statistics reported: total reads, reads flagged as human, replacement rate, verification pass/fail — all logged to console for every file processed.

The tool has built-in verification — it doesn't just write the output and hope for the best. After processing, it re-reads the output file and confirms that input and output read counts match exactly, every replaced read contains the expected synthetic prefix, and the original primers are intact. It reports statistics for every file: total reads, how many were flagged as human, the replacement rate, and whether verification passed. This gives you confidence the anonymization worked correctly.

PacBio 16S
Pipeline

Long-read microbiome sequencing with DADA2

Last tool. This is separate from the dietary metabarcoding work — it's about the microbiome. We're switching from Illumina to PacBio for 16S sequencing, and we needed a pipeline for that.

Where this fits

PacBio 16S is a parallel path—a different sequencer and pipeline, but it produces the same output format.

Here's how PacBio 16S fits into the bigger picture. The top row is the Illumina dietary metabarcoding workflow we've been talking about — trnL and 12S through Pipeline-to-Phyloseq. The PacBio 16S pipeline is a completely separate path — different sequencer, different chemistry, different marker — but it produces the same kind of output: a phyloseq object. So all our downstream analysis tools work the same way. The key difference is what it captures: trnL and 12S tell us what subjects eat, 16S tells us about their gut microbiome.

Why full-length 16S?

PacBio HiFi reads capture the entire 16S rRNA gene (~1500 bp), enabling species-level resolution that complements our dietary metabarcoding.

Short-read vs. long-read

  • Illumina V4: ~250 bp → genus-level classification
  • PacBio HiFi: ~1500 bp → species-level resolution
  • Full gene coverage eliminates primer-region bias

Lab context

  • trnL / 12S capture what subjects eat
  • 16S captures the gut microbiome response
  • Together: diet–microbiome relationships
Why PacBio? Illumina V4 gives you about 250 base pairs of the 16S gene — enough for genus-level classification but not species. PacBio HiFi reads capture the full gene, about 1500 base pairs, which gives us species-level resolution. That's a big deal for microbiome work. And it complements what we already do: trnL and 12S tell us what subjects eat, 16S tells us what their gut microbiome looks like. Together, we can study diet-microbiome relationships. The pipeline on the right shows the steps: primer removal with the universal 27F/1492R primers, length filtering for the expected 1000-to-1600 base pair range, DADA2 denoising with the PacBio-specific error function, chimera removal, GreenGenes2 taxonomy, and the final phyloseq object.

PacBio 16S: under the hood

Key design choices

  • PacBioErrfun — error model calibrated for HiFi reads (not Illumina defaults)
  • Orientation detection — primers found in both directions automatically
  • minFoldParentOverAbundance = 3.5 — conservative chimera threshold
  • minBoot = 50 — bootstrap confidence for taxonomy calls
  • Read tracking CSV — QC counts at every pipeline step

HPC infrastructure

  • 32 CPUs, 256 GB RAM, 5-day SLURM allocation
  • Singularity container for reproducibility
  • Scratch-based I/O for performance
  • Thread control to prevent over-subscription
  • Intermediate RDS saves for recovery

Output: a phyloseq object (ps_PacBio_16S.rds) with full taxonomy, chimera-free ASV table, and sample metadata—ready for downstream analysis.

Under the hood, a few key design choices. We use PacBioErrfun — DADA2's error model specifically calibrated for HiFi reads, not the Illumina defaults. Primers are detected in both orientations automatically. Chimera detection uses a conservative threshold of 3.5-fold parent overabundance. Taxonomy assignment uses GreenGenes2, the latest reference database, with a bootstrap confidence cutoff of 50. And there's a read tracking CSV that records counts at every step for QC. On the infrastructure side, this runs on DCC with 32 CPUs, 256 gigs of RAM, a 5-day SLURM allocation, and scratch-based I/O for performance. Intermediate objects are saved as RDS files so you can recover if something fails partway through. We've already used this for Auri's samples, and Caroline will be testing it on hers next.
